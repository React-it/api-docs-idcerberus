# Ready-made recipes

Use this page when you want to test a common flow without hunting service by service.

All the queries below use:

```txt
POST /api/service-api
Authorization: Bearer {jwt_token}
Content-Type: application/json
```

## Before testing

1. Generate a token in the same environment as the call.
2. Confirm the product has the service active and enabled for the API.
3. Use valid staging data.
4. For OCR, send the full base64 (with or without the `data:image/...;base64,` prefix, both work).
5. Read `result`, `status.message`, `onboardingStatus`, and `externalId`.

## Test CPF

Use this when you want to validate a simple individual query.

| Item | Value |
| --- | --- |
| Service | `SERVICE_PERSON_DATA_ENRICHMENT` |
| Required field | `cpf` |
| Curl example | [`service-api-cpf.hml.curl`](/examples/service-api-cpf.hml.curl) |

Payload:

```json
{
  "service": "SERVICE_PERSON_DATA_ENRICHMENT",
  "cpf": "00000000000"
}
```

Expected response:

```json
{
  "result": {
    "cpf": "00000000000",
    "name": "FICTITIOUS NAME",
    "birthDate": "2000-01-01",
    "status": "REGULAR"
  },
  "status": {
    "code": 200,
    "message": "Consulta realizada com sucesso"
  },
  "externalId": "..."
}
```

Common error:

```json
{
  "result": {},
  "status": {
    "code": 400,
    "message": "Don't have access to the service"
  },
  "onboardingStatus": "REFUSED",
  "externalId": "..."
}
```

## How to adapt a recipe

1. Swap only the `service` and the required fields.
2. Keep the `Authorization: Bearer {jwt_token}` header.
3. Use staging to validate the payload and data.
4. Don't automatically treat a missing field as an error.
5. Save `externalId` when you need to investigate.
