# Service families

The `POST /api/service-api` endpoint brings together different products.
Grouping by family helps you quickly find the right payload instead of
treating the endpoint as one long, undifferentiated list.

<Info>
  This page groups by product family. The full technical catalog, with
  every field and example for each service, lives in
  [Individual Services](/guides/servicos-pessoa-fisica) and
  [Business Services](/guides/servicos-pessoa-juridica). Use them as the
  reference source when you need a service's full contract.
</Info>

## How to use this page

1. Choose the service family.
2. Copy the `service` code or confirm the calling alias configured for the product.
3. Open `POST /api/service-api` in the API Reference.
4. Select the corresponding example.
5. Map the expected response.

## Consumption pattern

Every product on this page uses the same call base:

```json
{
  "service": "service_code",
  "cpf": "cpf"
}
```

The `service` field picks the product. The other fields vary by query:
document services use images or URLs, PF services use `cpf`, PJ services
use `cnpj`, and some certificates require extra data like `uf`, `rg`, or
`court`.

<Warning>
  The API validates `service` against the services enabled for the
  client's product. Because of this, in some cases the value sent in the
  call can be a short product alias, not another alias documented in the
  catalog.
</Warning>

Before testing with the client, confirm the alias for the product, copy
that value into the body, and then fill in the required fields for the
chosen family.

| Documented alias | Product's short alias |
| --- | --- |
| `SERVICE_DIGITAL_DOCUMENTOSCOPY` | `SERVICE_DOCUMENTOSCOPY` |
| `SERVICE_DIGITAL_DOCUMENTOSCOPY_CONSULT` | `SERVICE_DIGITAL_DOCUMENTOSCOPY` |
| `SERVICE_ECONOMIC_RELATIONSHIP` | `economic_relationships` |
| `SERVICE_EMAIL_VALIDATION` | `SERVICE_EMAIL_VALIDATION1` |
| `SERVICE_PROTEST_CLEARANCE_CERTIFICATE`, `SERVICE_PROTEST_PF` | `SERVICE_PROTEST_CLEARANCE_CERTIFICATE` |
| `SERVICE_PROTEST_PJ` | `SERVICE_PROTEST_CLEARANCE_CERTIFICATE_PJ` |

Think of `POST /api/service-api` as a runner. The route is always the
same, but the service executed changes based on the value sent in
`service`.

Example:

```json
{
  "service": "SERVICE_PERSON_DATA_ENRICHMENT",
  "cpf": "cpf"
}
```

In this case, the API understands it should run the individual data
enrichment service. If `service` changes, the product run changes too.

| Query type | Main document | Note |
| --- | --- | --- |
| Individual | `cpf` | May require extra data for certificates, validations, or biometrics |
| Business | `cnpj` | May require `uf` for state-level queries or complementary documents |
| Document and biometrics | `image1`, `image2`, `selfie1`, or URLs | Use base64 or a URL depending on the product |
| Onboarding/async document analysis | `key` | The key lets you query the result later |

<Tip>
  For implementation, copy the full example in the API Reference and use this page just to quickly pick the right product.
</Tip>

## Documents and biometrics

In this family, the payload needs extra care: a wrong image, base64 with a
prefix, or an incorrect alias can let the call authenticate and still not
produce the expected return. For OCR, also use the [OCR via Service API](/en/guides/service-api/sobre-ocr-service-api) guide.

| Product | `service` code | Main input |
| --- | --- | --- |
| React OCR | `SERVICE_OCR` | `documentType`, `image1`, `image2` |
| Emancipation OCR | `SERVICE_OCR_EMANCIPATION` | `image1` |
| Proof of address OCR | `SERVICE_OCR_PROOF_OF_ADDRESS` | `image1` |
| Face search in the base | `SERVICE_FACE_INDEX` | `image1` |
| FaceMatch | `SERVICE_FACE_MATCH` | `image1`, `image2` |
| Biometric score / CNH validation with DataValid | `SERVICE_DATAVALID_CNH` | `cpf`, `image1` |
| Digital document analysis | `SERVICE_DIGITAL_DOCUMENTOSCOPY` | `key`, `image1`, `image2`, `selfie1` |
| Document analysis result | `SERVICE_DIGITAL_DOCUMENTOSCOPY_CONSULT` | `key` |
