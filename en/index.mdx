## Shortest path (single-shot query via API)

<Steps>
  <Step title="Generate a token">
    Use `POST /api/token-generate` with the product's `client` and `secret`.
  </Step>
  <Step title="Choose the service">
    Open the [service index](/guides/indice-de-services) or the [API Reference](/api-reference/services-por-caso-de-uso) and copy the correct alias.
  </Step>
  <Step title="Build the payload">
    Send `service` and the product's required fields, such as `cpf`, `cnpj`, `image1`, `image2`, `documentType`, or `key`.
  </Step>
  <Step title="Run it in staging">
    Call `POST https://backoffice-hml.idcerberus.com/api/service-api` with `Authorization: Bearer {jwt_token}`.
  </Step>
  <Step title="Read the result">
    Use `result` as the business return and `status.message`, `onboardingStatus`, and `externalId` for diagnostics.
  </Step>
</Steps>

<Info>
  Going to capture the user's document and selfie in a guided registration, instead of making single-shot queries? That's the onboarding flow via SDK or Web Client. See [Onboarding via SDK](/en/guides/onboarding-sdk) instead of the steps above.
</Info>

## Integration models

| Model | When to use | What you implement |
| --- | --- | --- |
| Direct API | Server-to-server queries by CPF, CNPJ, image, or key | Token, payload, HTTP call, and reading `result` |
| SDK | Guided capture of document, selfie, and data in the app | Generating `tokenOnboarding` and querying the result (or receiving it via webhook) |
| Web Client | Flows in WebView, browser, or QR Code | Redirecting the user and reading the processing status |
| Webhook | Complements any model above: notifies your application when the status changes, for onboarding or single-shot queries | Configuring the receiving URL and validating the `id-cerberus-token` header |

## Essential endpoints

| Operation | Endpoint | Use |
| --- | --- | --- |
| Generate token | `POST /api/token-generate` | Authenticate protected calls |
| Run service | `POST /api/service-api` | Run CPF, CNPJ, OCR, biometrics, risk, and compliance checks |
| Generate TokenOnboarding | `POST /api/token-history-onboarding` | Start a flow via SDK |
| Query onboarding | `GET /api/onboarding/report/{tokenOnboarding}` | Get status, fields, and processed rules |
| Download PDF report | `GET /api/history-onboarding-report/{tokenOnboarding}` | Store or audit the final result |

## Quick example

Generate a token:

```bash
curl --location 'https://backoffice-hml.idcerberus.com/api/token-generate' \
  --header 'Content-Type: application/json' \
  --data '{
    "client": "{client}",
    "secret": "{secret}"
  }'
```

Use the token to run a query:

```bash
curl --location 'https://backoffice-hml.idcerberus.com/api/service-api' \
  --header 'Authorization: Bearer {jwt_token}' \
  --header 'Content-Type: application/json' \
  --data '{
    "service": "SERVICE_PERSON_DATA_ENRICHMENT",
    "cpf": "00000000000"
  }'
```

## Response pattern

Most services return the useful data in `result` and the technical status in `status`.

```json
{
  "result": {},
  "status": {
    "code": 200,
    "message": "Success"
  },
  "onboardingStatus": "APPROVED",
  "externalId": "..."
}
```

<Note>
  The `service` field defines which product runs inside `POST /api/service-api`. The other fields change depending on the query chosen.
</Note>
