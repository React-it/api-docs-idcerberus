Use esta página quando uma chamada não funcionar como esperado.

## Recebi 401 ou 403 (HTTP)

Em `POST /api/service-api`, um HTTP 401/403 de verdade só acontece por
problema de autenticação: a chamada nem chega a processar o service.

1. Token ausente.
2. Token expirado.
3. Token gerado em outro ambiente.

Como resolver:

1. Gere um novo token.
2. Confirme se a URL é de HML ou produção.
3. Envie o header:

```txt
Authorization: Bearer {jwt_token}
```

<Warning>
  "Produto não liberado para a conta" e "service sem permissão" **não** geram
  HTTP 401/403 nesse endpoint. A chamada retorna HTTP 200 com o problema
  descrito em `status.message` (`status.code` 400 ou 401 dentro do corpo).
  Veja a seção seguinte.
</Warning>

## HTTP 200, mas `status.code` diferente de 200

Esse é o caso mais comum de erro em `POST /api/service-api`: a chamada
"funcionou" no sentido HTTP, mas o corpo mostra o problema real.

| `status.code` no corpo | Causa | Observação |
| --- | --- | --- |
| 400 | Body inválido, campo obrigatório ausente, `service` incorreto, CPF/CNPJ inválido, fonte externa indisponível | Leia `status.message` para o motivo exato |
| 401 | Produto não encontrado ou inativo para o `client` usado | Diferente do HTTP 401: aqui o token é válido, o produto que está desativado |

Como resolver:

1. Leia `status.message`.
2. Confira se o body está em JSON válido.
3. Confira se enviou `Content-Type: application/json`.
4. Confira se o campo `service` está correto.
5. Compare o body com o exemplo da API Reference.

## O token funciona em HML, mas não em produção

Token e URL precisam ser do mesmo ambiente.

| Ambiente | URL |
| --- | --- |
| HML | `https://backoffice-hml.idcerberus.com` |
| Produção | `https://backoffice.idcerberus.com` |

Gere um token novo em produção usando credenciais de produção.

## O cURL funciona, mas meu código não

Confira:

1. URL base.
2. Método HTTP.
3. Headers.
4. Body JSON.
5. Timeout.
6. Serialização do JSON.
7. Header `Authorization`.
8. Header `Content-Type`.

Compare o request do código com o request da API Reference.

## O PowerShell quebra o comando cURL

No Windows, use `curl.exe` em vez de `curl`.

```powershell
curl.exe --location "https://backoffice-hml.idcerberus.com/api/token-generate" `
  --header "Content-Type: application/json" `
  --data "{\"client\":\"{client}\",\"secret\":\"{secret}\"}"
```

O comando `curl` sozinho pode ser interpretado pelo PowerShell como outro alias.

## A consulta retornou sucesso, mas não veio o dado esperado

Nem todo retorno sem dado é erro técnico.

Exemplos:

1. certidão com “Nada consta”;
2. CPF não encontrado em validação de endereço;
3. pessoa não exposta politicamente;
4. empresa sem débitos;
5. lista vazia de relacionamentos.

Leia `result` e aplique a regra de negócio do seu produto.

## A resposta não veio em JSON

Alguns endpoints retornam outro tipo de conteúdo. Exemplo:

```txt
GET /api/history-onboarding-report/{tokenOnboarding}
```

Esse endpoint retorna PDF, não JSON.

## Checklist rápido

Antes de pedir apoio, confira:

1. A URL está correta?
2. O método HTTP está correto?
3. O token foi gerado no mesmo ambiente?
4. O header `Authorization` foi enviado?
5. O header `Content-Type` foi enviado?
6. O body é JSON válido?
7. O campo `service` está correto?
8. O CPF/CNPJ está no campo esperado?
9. O serviço está liberado para a conta?
10. Você leu `status.message`?
