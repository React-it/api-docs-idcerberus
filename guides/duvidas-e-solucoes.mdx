# Dúvidas e Soluções

Esta página reúne, num só lugar, as perguntas que mais aparecem durante uma
integração com a idCerberus. A ideia é simples: antes de abrir um chamado de
suporte, procure sua dúvida aqui. Boa parte dos "bugs" reportados são
comportamentos esperados que só não estavam claros na documentação técnica.

<Tip>
  Use `Ctrl + F` (ou `Cmd + F` no Mac) para pesquisar uma palavra-chave nesta
  página antes de percorrer as seções manualmente.
</Tip>

## Autenticação e token

<AccordionGroup>
  <Accordion title="Preciso gerar um token novo a cada chamada?">
    Não. Gere um `access_token` em `POST /api/token-generate` e reutilize até
    ele expirar, conforme o campo `expires_in` do retorno. Gerar um novo a
    cada chamada funciona, mas desperdiça uma chamada extra por request.
  </Accordion>
  <Accordion title="O que acontece se eu chamar a API com o token expirado?">
    Você recebe HTTP 401. Gere um token novo com `client` e `secret` e repita
    a chamada original. Isso é um HTTP de verdade, diferente das falhas de
    permissão de service que também aparecem como "401 no corpo" (veja a
    seção de status abaixo).
  </Accordion>
  <Accordion title="client e secret são os mesmos em HML e produção?">
    Não. São credenciais diferentes por ambiente. Um `client`/`secret` de HML
    não gera token válido para chamar produção, e vice-versa — os bancos de
    dados e o realm de autenticação são separados fisicamente entre os dois
    ambientes.
  </Accordion>
  <Accordion title="Ainda não tenho client e secret. O que faço?">
    Esse par é liberado pela React IT junto com o produto contratado, não é
    algo que você gera sozinho. Solicite pelo e-mail
    [contact@react-it.com](mailto:contact@react-it.com).
  </Accordion>
</AccordionGroup>

## Consulta avulsa (POST /api/service-api)

<AccordionGroup>
  <Accordion title="Recebi HTTP 200, mas a consulta não funcionou. Isso é normal?">
    Sim, e é o motivo número um de confusão nesta API. `POST /api/service-api`
    quase sempre retorna HTTP 200, mesmo quando a consulta falhou por
    completo — o motivo real fica dentro do corpo, em `status.code` e
    `status.message`. Nunca decida sucesso ou falha só pelo HTTP status.
  </Accordion>
  <Accordion title="Qual a diferença entre um 401/403 de verdade e um erro de acesso no corpo?">
    HTTP 401/403 de verdade só acontece por problema de autenticação — token
    ausente, expirado ou de outro ambiente — e a chamada nem chega a
    processar o service. "Produto não liberado para o service" e "produto
    inativo" não geram HTTP 401/403 nesse endpoint: a chamada retorna HTTP
    200 com o problema descrito em `status.code` (400 para payload/permissão
    de service, 401 para produto inativo ou não encontrado) dentro do corpo.
  </Accordion>
  <Accordion title="A chamada voltou 200/200, mas result veio vazio. Por quê?">
    Existem pelo menos três causas distintas: a fonte de dados não encontrou
    nada para aquele documento (comportamento válido — nem todo retorno vazio
    é erro), a imagem não foi lida com sucesso em OCR, ou — se o seu produto
    for pré-pago — o saldo da organização está insuficiente. Esse último caso
    é traiçoeiro porque também vem com HTTP 200 e `status.code` 200, com
    `status.message` dizendo algo como "Not enough balance". Sempre leia
    `status.message` quando `result` vier vazio, mesmo com 200/200.
  </Accordion>
  <Accordion title="O alias que estou usando pode ser diferente em outro produto?">
    Não. O alias de cada service (o valor que você envia em `service`) é
    único no sistema — não existe um alias customizado por produto. Se um
    service não funciona, o problema é ele não estar habilitado para o seu
    produto, não o nome do alias estar errado (a menos que você tenha
    digitado errado).
  </Accordion>
  <Accordion title="Um alias parece ter erro de digitação. Devo corrigir?">
    Só num caso específico: `SEVICE_ONLINE_BETTING_PROPENSITY` está
    documentado sem a letra R em `SERVICE` de propósito — essa é a grafia
    implementada no backend. Corrigir esse alias ao copiar quebra a chamada.
    Fora esse caso, copie os aliases exatamente como aparecem no
    [catálogo de services](/guides/indice-de-services).
  </Accordion>
</AccordionGroup>

## Onboarding via SDK ou Cliente Web

<AccordionGroup>
  <Accordion title="access_token e tokenOnboarding são a mesma coisa?">
    Não, e confundir os dois é uma fonte comum de erro. `access_token`
    autentica a sua aplicação e expira em minutos. `tokenOnboarding`
    identifica um cadastro específico e continua válido durante todo o
    processo, mesmo depois do `access_token` expirar. Se o `access_token`
    expirar no meio do fluxo, gere um novo — o `tokenOnboarding` não muda.
  </Accordion>
  <Accordion title="Quanto tempo leva para um onboarding sair de IN_PROCESS?">
    Não há um tempo fixo garantido. O processamento automático é verificado a
    cada poucos segundos internamente, mas o tempo total depende de quantos
    services estão na esteira e se algum deles depende de fontes externas
    lentas. Trate como comportamento observado, não como SLA contratual, e
    sempre implemente um limite máximo de espera na sua aplicação.
  </Accordion>
  <Accordion title="REFUSED é um erro que devo tratar como falha técnica?">
    Não. `REFUSED` é um resultado de negócio — a chamada em si teve sucesso
    (HTTP 200), e o cadastro é que não foi aprovado pelas regras do produto.
    Não trate `REFUSED` como algo para repetir a chamada; trate como decisão
    que a sua aplicação precisa refletir para o usuário.
  </Accordion>
</AccordionGroup>

## Webhooks

<AccordionGroup>
  <Accordion title="Configurei o webhook e não recebi nada. O que houve?">
    Primeiro, confirme que o evento que você espera realmente dispara
    webhook: mudança de status de onboarding, decisão de revisão manual, e
    consulta avulsa em `POST /api/service-api` (quando o produto tem webhook
    configurado). Segundo, lembre que consulta avulsa dispara o webhook cerca
    de 10 segundos depois da resposta HTTP, não instantaneamente. Terceiro,
    valide se a sua URL está acessível publicamente (a idCerberus não
    consegue entregar num endpoint atrás de firewall sem liberação).
  </Accordion>
  <Accordion title="Meu endpoint falhou ao processar um evento. Ele será reenviado sozinho?">
    Não. Não existe um processo automático que fica reenviando entregas que
    falharam. Um novo envio só acontece se o mesmo onboarding mudar de
    conteúdo de novo mais tarde (o que dispara como uma entrega nova, não
    como retry), ou se alguém com acesso ao [Backoffice](/guides/backoffice)
    forçar o reenvio manualmente na tela. Por isso, nunca dependa só do
    webhook — mantenha o polling (`GET /api/onboarding/report/{tokenOnboarding}`)
    como rede de segurança de verdade.
  </Accordion>
  <Accordion title="O payload do webhook muda dependendo de onde ele veio?">
    Sim. Webhook originado de onboarding usa o formato de relatório completo
    (`tokenOnboarding`, `status`, `fields`, `services`). Webhook originado de
    consulta avulsa usa o mesmo JSON que já veio na resposta HTTP síncrona da
    chamada (`result`, `status`, `onboardingStatus`, `externalId`) — são
    formatos diferentes, então não assuma uma estrutura única.
  </Accordion>
</AccordionGroup>

## OCR e imagem

<AccordionGroup>
  <Accordion title="Preciso remover o prefixo data:image/...;base64, antes de enviar?">
    Não. O sistema aceita base64 com ou sem esse prefixo e remove
    automaticamente quando presente. Se a sua ferramenta gera o base64 com
    prefixo (comum em navegador, por exemplo), não perca tempo removendo.
  </Accordion>
  <Accordion title="O OCR retornou vazio mesmo com uma imagem boa. O que conferir?">
    Confirme três coisas na ordem: se o `documentType` bate com o documento
    real enviado, se a imagem está completa e legível (sem corte nas bordas),
    e se o base64 não foi truncado no meio do envio — esse último é comum
    quando o payload é montado manualmente e o corte acontece sem erro
    visível até chegar na API.
  </Accordion>
  <Accordion title="O campo com o tipo de documento se chama docType ou doc?">
    Pode variar. `SERVICE_OCR` é processado por parceiros diferentes conforme
    a configuração do seu produto, e isso pode mudar um campo pontual do
    `result` — o mais comum é o nome do campo que indica o tipo do documento
    reconhecido. Trate o contrato desta página como "os campos costumam vir
    assim", não como uma garantia rígida campo a campo, e sempre valide pelo
    `result` retornado no seu ambiente real.
  </Accordion>
</AccordionGroup>

## Backoffice

<AccordionGroup>
  <Accordion title="Meu login do backoffice funciona para gerar token de API?">
    Não. São dois mecanismos de autenticação diferentes para o mesmo sistema.
    O login do backoffice é usuário e senha, pessoal. `client` e `secret`
    autenticam a sua aplicação e geram `access_token` via
    `POST /api/token-generate`. Veja [Autenticação](/guides/autenticacao)
    para o lado API.
  </Accordion>
  <Accordion title="Consigo configurar o webhook pelo backoffice?">
    A configuração de webhook (URL e chave) hoje é feita pela React IT sob
    pedido, não é uma tela de autoatendimento ainda. Veja
    [Webhooks](/guides/webhooks) para como pedir a ativação.
  </Accordion>
  <Accordion title="Por que a URL da API se chama backoffice-hml.idcerberus.com?">
    `backoffice-hml.idcerberus.com` e `backoffice.idcerberus.com` são as
    mesmas URLs usadas pelo painel administrativo — mas quando você chama
    `/api/...` nelas, está falando com a API, não com a interface visual. Não
    existe uma URL separada só para API: é o mesmo domínio, endpoints
    diferentes.
  </Accordion>
</AccordionGroup>

## Ambientes

<AccordionGroup>
  <Accordion title="Posso testar em produção sem impacto, só pra ver o retorno?">
    Não recomendado. Homologação e produção usam bancos de dados e
    credenciais completamente separados. Teste sempre em HML primeiro; use
    produção só depois de validar o fluxo, com dados reais e consciência de
    que consultas em produção normalmente têm custo.
  </Accordion>
  <Accordion title="Um erro que só acontece em produção e não em HML. Por onde começo?">
    Confirme, nesta ordem: se o token usado é de produção (não HML), se o
    produto de produção tem os mesmos services habilitados que o de HML, e
    se a massa de dados testada em produção é real (HML costuma ter dados
    fake que não existem nas fontes de produção). Divergência de
    configuração entre ambientes é a causa mais comum aqui.
  </Accordion>
</AccordionGroup>

## Antes de abrir chamado

Se sua dúvida não está aqui, reúna estas informações antes de acionar o
suporte — isso evita idas e vindas e acelera a resposta.

| Informação | Onde encontrar |
| --- | --- |
| Ambiente (HML ou produção) | A base URL usada na chamada |
| `service` enviado | O campo `service` do seu payload |
| `status.code` e `status.message` | O corpo da resposta, não o HTTP status |
| `externalId` | Retornado no corpo, quando presente |
| Horário aproximado da chamada | Para cruzar com os logs internos |

Veja o formato completo de chamado em
[Erros comuns de integração](/guides/erros-comuns-integracao#como-solicitar-suporte).
